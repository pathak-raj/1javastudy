1. Requirements and Architecture

1. Functional & Non-Functional Requirements

  • Functional:
  • Capture INFO, WARN, and ERROR logs (with full multi-line stack traces) from all Java microservices.
  • Correlate logs from a single user request across multiple services using a shared traceId.
  • Real-time search, filtering, and automated alerting on ERROR spikes.
  • Tiered log retention (Hot, Warm, Cold) based on severity and compliance rules.
  • Non-Functional:
  • Zero App Latency Impact: Logging must never block business threads (neverBlock=true).
  • High Availability & At-Least-Once Delivery: Survive Pod crashes (OOMKilled), traffic surges, and downstream storage downtime without losing ERROR logs.
  • Cost Efficiency: Compress and tier high-volume INFO logs aggressively while preserving critical ERROR and audit trails.

2. Component Design

3. Component-by-Component Deep Dive

A. Java Microservice Layer (Generation & Correlation)

  • Logging Stack: SLF4J + Logback (AsyncAppender with neverBlock=true) + logstash-logback-encoder.
  • Why Single-Line JSON? Java ERROR stack traces contain 50+ newlines. Escaping newlines inside a single JSON string ensures downstream log shippers never split one exception into 50 broken log entries.
  • Cross-Service Tracing: Attach the OpenTelemetry Java Agent (-javaagent:opentelemetry-javaagent.jar). It propagates W3C traceparent headers across REST, gRPC, and Kafka calls and injects traceId and spanId into SLF4J's MDC automatically.
  • Dynamic Log Levels: Expose Spring Boot Actuator (/actuator/loggers) internally so on-call engineers can temporarily toggle a misbehaving microservice to DEBUG for 10 minutes without restarting Pods.

B. Pod & Node Collection Layer (Kubernetes)

  • Node-Level DaemonSet (Fluent Bit): Run 1 Fluent Bit Pod per Worker Node instead of a sidecar per app Pod. It consumes ~40MB RAM per node and serves all microservice Pods on that host.
  • Crash Safety (OOMKilled): Because Java writes to stdout, Kubernetes (containerd) writes logs directly to the Worker Node's disk (/var/log/containers/*.log). Even if a microservice Pod crashes abruptly, its final ERROR logs remain on the node disk and are shipped via Fluent Bit's persistent SQLite offset tracker.
  • Disk Guardrails: Set kubelet containerLogMaxSize: 50Mi and containerLogMaxFiles: 5 so a chatty INFO loop cannot fill up the Worker Node's disk.

C. Buffering & Stream Processing Layer

  • Apache Kafka (72-Hour Buffer): Acts as a shock absorber during cascading outage storms and protects against log loss if OpenSearch goes down for maintenance.
  • logs-critical (ERROR, WARN): Dedicated partitions and high-priority consumers for sub-3-second indexing and alerting.
  • logs-standard (INFO): Separate consumer group that can lag safely under peak load.
  • Stream Processor (Vector / Logstash):

1. Filter: Drops zero-value Kubernetes /healthz and /metrics probe logs (~30% volume reduction).

2. Sanitize: Redacts PII, passwords, and bearer tokens before storage.

3. Deduplicate: Collapses identical stack traces occurring within 10 seconds into one event with a repeat_count field.

D. Storage & Multi-Tier Retention Strategy

Log Level | Hot Tier (NVMe SSD — OpenSearch/Loki) | Warm Tier (HDD / UltraWarm) | Cold Tier (S3/GCS Parquet + Zstd) | Total Retention

ERROR | 30 days (Daily index: logs-error-*) | 60 days (Days 31–90) | 1–7 years | Up to 7 years

WARN | 14 days (Daily index: logs-warn-*) | 30 days (Days 15–44) | 1 year | 1 year

INFO | 5 days (Daily index: logs-info-*) | None (Skipped) | 90 days | 90 days

Audit Logs | 30 days | 90 days | 7 years (S3 Object Lock WORM) | 7 years

  • Automated Lifecycle: OpenSearch Index State Management (ISM) moves indices from Hot → Warm (force-merged to 1 segment, replicas reduced to 1) → Delete. Simultaneously, a Kafka S3 Sink writes compressed Parquet files to S3/GCS, queryable on-demand via AWS Athena or Trino.

3. Failure Modes

4. Failure Modes & How the System Survives Them

Failure Scenario | System Behavior & Recovery

Microservice Pod crashes (OOMKilled) | Final ERROR stack trace is already flushed to node disk /var/log/containers; Fluent Bit DaemonSet reads the remaining offset and ships it to Kafka.

Cascading outage causes 50x ERROR spike | Java AsyncAppender never blocks app threads; Kafka absorbs the burst on disk; stream processor deduplicates repetitive stack traces; logs-critical stays isolated from INFO traffic.

OpenSearch / Storage cluster goes down | Stream processor pauses consumption; Kafka retains all logs safely on disk for up to 72 hours; once OpenSearch recovers, consumers catch up automatically.

Kafka brokers become temporarily unreachable | Fluent Bit buffers batches in its local filesystem chunk storage on each Worker Node (storage.type filesystem) and retries with exponential backoff until Kafka recovers.

4. Worker Node Logs vs Central Hot Storage

No, they are two completely different disks at opposite ends of the pipeline.

  • Host Disk (/var/log/containers/*.log): This is the temporary local disk on your Kubernetes Worker Node (an ephemeral buffer). It only holds raw logs for a few minutes/hours until Fluent Bit reads them and sends them to Kafka.
  • Hot Tier Disk (NVMe SSDs in OpenSearch / Loki): This is the centralized storage cluster at the end of the pipeline where logs live for 5 to 30 days so engineers can search and filter them in Kibana or Grafana.

Side-by-Side Comparison

Attribute | Kubernetes Node Host Disk (/var/log/containers) | Centralized "Hot Tier" Disk (OpenSearch / Loki)

Where does it live? | On every individual Kubernetes Worker Node (EC2 / VM). | On dedicated OpenSearch/Elasticsearch database servers.

What is its job? | Temporary landing zone so Pod logs survive crashes before shipping. | Centralized search database for querying across all microservices.

How long do logs stay? | Minutes to a few hours (rotated once 5 files × 50MB = 250MB per container is hit). | 5 to 30 days (fast NVMe SSDs for instant Kibana/Grafana queries).

Can you search it? | No (only raw text files on individual nodes). | Yes (full-text search by traceId, level, service, and time range).

5. Docker Images, Pods and Node Logging

But pod run docker image?

Yes, a Pod runs a container built from your Docker image—and that is the exact reason logs end up on the Worker Node's host disk (/var/log/containers).

A container is just an isolated Linux process running directly on the Worker Node's kernel (not a separate virtual machine). When your Java app inside the Docker container prints to stdout (System.out.println / Logback ConsoleAppender), the container runtime (containerd or Docker Engine) running on the Worker Node intercepts that stdout stream and automatically writes it to a file on the Worker Node's disk.

Why This Works So Cleanly

1. Zero Storage Used Inside Your Docker Image: Your Java container's writable layer never grows or fills up with log files. You don't need to mount persistent volumes (PVCs) into every microservice Pod just to save logs.

2. Built Into Kubernetes (kubectl logs): Have you ever run kubectl logs <pod-name>? Kubernetes simply reads that exact /var/log/containers/*.log file on the Worker Node and streams it back to your terminal.

3. Fluent Bit Reads the Same File: The Fluent Bit DaemonSet Pod mounts the Worker Node's /var/log directory as a hostPath volume. That allows Fluent Bit to read the stdout logs of every Docker container running on that Worker Node without needing to enter or modify any of your microservice containers.

Quick Summary of the Docker → Pod → Disk Chain

  • Your Dockerfile packages your Java .jar + OpenTelemetry agent and runs java -jar app.jar.
  • Logback prints JSON to stdout (the console).
  • Kubernetes (containerd) catches everything printed to stdout and saves it on the Worker Node's /var/log/containers/*.log.
  • Fluent Bit picks up those files from /var/log/containers/*.log and forwards them to Kafka → OpenSearch/S3.

6. Loki, OpenSearch and Prometheus

Neither Loki nor Prometheus sits after OpenSearch/S3—they serve completely different roles in the observability stack:

  • Grafana Loki is an alternative to OpenSearch (it stores and indexes logs). You choose either OpenSearch or Loki as your log database—not both.
  • Prometheus is for metrics (numbers/time-series) like CPU usage, HTTP error counts, and latency—not text logs (INFO, WARN, ERROR).

1. OpenSearch vs. Grafana Loki (Which Log Storage Should You Pick?)

Since you already mentioned Loki, here is how to decide between OpenSearch and Grafana Loki at the end of your pipeline:

Feature | OpenSearch / Elasticsearch | Grafana Loki

How it indexes logs | Indexes every single word/field inside the JSON log body. | Indexes only metadata labels (service, namespace, level, traceId), leaving the log message compressed as raw text.

Search speed | Ultra-fast arbitrary full-text searches (e.g., searching for a random customer email across 10TB). | Fast when filtering by labels (service="payment", level="ERROR"), slower for unindexed wildcard text scans.

Storage & Infra Cost | High (requires heavy RAM + NVMe SSD clusters for inverted indices). | Very Low (~70% cheaper) — Loki writes compressed log chunks straight to Amazon S3 / GCS natively!

Best UI | OpenSearch Dashboards / Kibana | Grafana (integrates seamlessly with Prometheus metrics).

Rule of Thumb:

  • Pick OpenSearch if your teams run heavy ad-hoc full-text queries across massive log bodies and have the budget for large SSD clusters.
  • Pick Grafana Loki if you already use Prometheus + Grafana, query logs primarily by service, level (INFO/WARN/ERROR), and traceId, and want native S3 storage without managing separate Hot/Warm SSD tiers.

2. Where Does Prometheus Fit?

Prometheus does not read logs from Kafka or OpenSearch. Instead, it scrapes numeric metrics directly from your microservices' /actuator/prometheus endpoint every 15 seconds:

  • Prometheus tells you what is wrong: "Payment-service HTTP 500 error rate jumped from 0.1% to 12% at 18:45."
  • Loki / OpenSearch tells you why it is wrong: "Here is the exact Java NullPointerException stack trace for traceId: abc-123."
